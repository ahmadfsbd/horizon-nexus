You are implementing a production-grade OpenStack Horizon rebranding system called "Horizon Nexus".
The goal is a fully automated pipeline that tracks multiple OpenStack releases, detects upstream
Kolla Horizon image changes via digest comparison, builds a themed container per release, and
pushes versioned images to Docker Hub under ahmadfsbd/horizon-nexus.

================================================================================
CONSTRAINTS (non-negotiable)
================================================================================

- Never modify upstream Horizon source files
- All customisation lives in the overlay/ directory only
- Template overrides must use Django block inheritance with the ! prefix to reference
  upstream templates (e.g. {% extends "!base.html" %}) — never full template copies
- The Dockerfile takes HORIZON_TAG as a build argument so the same file builds any release
- CI is GitHub Actions only
- Docker Hub namespace: ahmadfsbd/horizon-nexus
- fail-fast: false on all matrix jobs — one release failing must not block others
- Digest-based change detection (not tag name) — Kolla can repush to the same tag silently

ACCENT COLOUR SYSTEM
================================================================================

Primary accent: #3c7d7d

Derive and use this full palette throughout all SCSS and templates:
  --nexus-accent:         #3c7d7d   (primary: nav bar, buttons, active states)
  --nexus-accent-dark:    #2d5f5f   (hover states, active elements)
  --nexus-accent-light:   #5aa3a3   (secondary highlights)
  --nexus-accent-subtle:  #e8f4f4   (backgrounds, selected rows, table headers)
  --nexus-text-on-accent: #ffffff   (text rendered on accent-coloured backgrounds)

Apply accent to:
  - Top navigation bar background
  - Active tab indicator (white underline border-bottom on dark bg)
  - Primary buttons
  - Focus rings
  - Link hover colour
  - Table row selected state
  - Table header background (use --nexus-accent-subtle)

IMPORTANT — implement all accent colours as CSS custom properties in :root,
not as hardcoded SCSS values. This is required so they can be overridden at
deploy time via Kolla config injection without rebuilding the image:

In nexus.scss, define:
  :root {
    --nexus-accent:        #3c7d7d;
    --nexus-accent-dark:   #2d5f5f;
    --nexus-accent-light:  #5aa3a3;
    --nexus-accent-subtle: #e8f4f4;
  }

Then reference only var(--nexus-accent) etc. throughout all CSS rules.
Never hardcode the hex values directly in rules — always go through the
CSS variable. This is what makes deployment-time colour overrides possible.

Also create overlay/themes/nexus/static/css/nexus-vars.css as a standalone
file containing only the :root block above. This file is the one Kolla
operators replace at deploy time to change the colour scheme without touching
the image. The compiled nexus.css loads this file last so it takes precedence.

.github/workflows/build.yml

name: Build and Push

on:
  push:
    branches: [main]
  workflow_dispatch:
    inputs:
      release:
        description: 'Specific release name to build (empty = all)'
        required: false
        default: ''
  workflow_call:
    inputs:
      release:
        type: string
        required: false
        default: ''

jobs:
  prepare:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.set-matrix.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - name: Build release matrix
        id: set-matrix
        run: |
          if [ -n "${{ inputs.release }}" ]; then
            MATRIX=$(jq -c \
              --arg r "${{ inputs.release }}" \
              '[.releases[] | select(.name == $r)]' \
              releases.json)
          else
            MATRIX=$(jq -c '.releases' releases.json)
          fi
          echo "matrix=$MATRIX" >> $GITHUB_OUTPUT

  build:
    needs: prepare
    runs-on: ubuntu-latest
    strategy:
      matrix:
        release: ${{ fromJson(needs.prepare.outputs.matrix) }}
      fail-fast: false
    steps:
      - uses: actions/checkout@v4

      - name: Set image tags
        run: |
          UI_VERSION=$(cat VERSION)
          echo "PINNED_TAG=${{ matrix.release.name }}-${UI_VERSION}" >> $GITHUB_ENV
          echo "FLOAT_TAG=${{ matrix.release.name }}-latest"         >> $GITHUB_ENV
          echo "KOLLA_TAG=${{ matrix.release.kolla_tag }}"           >> $GITHUB_ENV

      - name: Compile SCSS
        run: |
          npm install -g sass
          sass overlay/themes/nexus/static/scss/nexus.scss \
               overlay/themes/nexus/static/css/nexus.css \
               --no-source-map

      - name: Build image
        run: |
          docker build \
            --build-arg HORIZON_TAG=${{ env.KOLLA_TAG }} \
            -t ahmadfsbd/horizon-nexus:${{ env.PINNED_TAG }} \
            -t ahmadfsbd/horizon-nexus:${{ env.FLOAT_TAG }} \
            .

      - name: Smoke test
        run: |
          docker run -d \
            --name test-${{ matrix.release.name }} \
            -p 8080:80 \
            ahmadfsbd/horizon-nexus:${{ env.PINNED_TAG }}
          sleep 8
          curl -sf http://localhost:8080/auth/login/ \
            | grep -q "nexus-nav" \
            || (echo "FAIL: nexus-nav element not found for \
                ${{ matrix.release.name }}" && exit 1)
          docker stop test-${{ matrix.release.name }}

      - name: Push to Docker Hub
        run: |
          echo ${{ secrets.DOCKERHUB_TOKEN }} | \
            docker login -u ${{ secrets.DOCKERHUB_USERNAME }} --password-stdin
          docker push ahmadfsbd/horizon-nexus:${{ env.PINNED_TAG }}
          docker push ahmadfsbd/horizon-nexus:${{ env.FLOAT_TAG }}

      - name: Notify on failure
        if: failure()
        uses: actions/github-script@v7
        with:
          script: |
            await github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: `Build failed: ${{ matrix.release.name }}`,
              body: `The build and push pipeline failed for release **${{ matrix.release.name }}**.\n\nRun: ${context.serverUrl}/${context.repo.owner}/${context.repo.repo}/actions/runs/${context.runId}`,
              labels: ['build-failure']
            });

# ahmadfsbd/horizon-nexus:latest is NOT auto-pushed.
# Promote manually by tagging and pushing a specific pinned image as latest.

.github/workflows/upstream-check.yml
================================================================================

name: Upstream Version Check

on:
  schedule:
    - cron: '0 9 * * 1'
  workflow_dispatch:

jobs:
  load:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.load.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - id: load
        run: |
          echo "matrix=$(jq -c '.releases' releases.json)" >> $GITHUB_OUTPUT

  check:
    needs: load
    runs-on: ubuntu-latest
    strategy:
      matrix:
        release: ${{ fromJson(needs.load.outputs.matrix) }}
      fail-fast: false
    permissions:
      contents: write
      actions: write

    steps:
      - uses: actions/checkout@v4

      - name: Check digest for ${{ matrix.release.name }}
        id: digest-check
        run: |
          TAG="${{ matrix.release.kolla_tag }}"
          DIGEST_FILE="digests/${TAG}.txt"

          LATEST=$(curl -s \
            "https://hub.docker.com/v2/repositories/kolla/ubuntu-binary-horizon/tags/${TAG}" \
            | jq -r '.images[0].digest // ""')

          STORED=""
          if [ -f "$DIGEST_FILE" ]; then STORED=$(cat "$DIGEST_FILE"); fi

          echo "latest=$LATEST"             >> $GITHUB_OUTPUT
          echo "stored=$STORED"             >> $GITHUB_OUTPUT
          echo "tag=$TAG"                   >> $GITHUB_OUTPUT
          echo "digest_file=$DIGEST_FILE"   >> $GITHUB_OUTPUT

          if [ -n "$LATEST" ] && [ "$LATEST" != "$STORED" ]; then
            echo "changed=true"  >> $GITHUB_OUTPUT
          else
            echo "changed=false" >> $GITHUB_OUTPUT
          fi

      - name: Update stored digest
        if: steps.digest-check.outputs.changed == 'true'
        run: |
          mkdir -p digests
          echo "${{ steps.digest-check.outputs.latest }}" \
            > "${{ steps.digest-check.outputs.digest_file }}"

      - name: Trigger build for ${{ matrix.release.name }}
        if: steps.digest-check.outputs.changed == 'true'
        uses: actions/github-script@v7
        with:
          script: |
            await github.rest.actions.createWorkflowDispatch({
              owner: context.repo.owner,
              repo: context.repo.repo,
              workflow_id: 'build.yml',
              ref: 'main',
              inputs: { release: '${{ matrix.release.name }}' }
            });
            console.log('Build triggered for ${{ matrix.release.name }}');

  commit-digests:
    needs: check
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
      - name: Commit updated digests
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add digests/
          git diff --staged --quiet \
            || git commit -m "chore: update upstream digests [skip ci]"
          git push

README.md — document all of the following sections
================================================================================

1. Architecture overview — upstream base + overlay pattern, why no fork

2. How automatic builds work — two triggers explained:

   TRIGGER 1 — YOUR OVERLAY CHANGES (immediate):
   Any push to main triggers build.yml and rebuilds all four release images
   automatically with no human intervention required.

   TRIGGER 2 — UPSTREAM KOLLA CHANGES (weekly digest check):
   Every Monday at 9am UTC, upstream-check.yml runs across all releases in
   releases.json. It compares the current Docker Hub image digest of each
   Kolla Horizon tag against the digest stored in the digests/ folder.
   If a digest has changed, it automatically triggers build.yml for that
   specific release only. The new image is built, smoke tested, and pushed
   to ahmadfsbd/horizon-nexus:<release>-latest without any human intervention.

   If Kolla pushes a new antelope image on a Wednesday, the pipeline catches
   it the following Monday and automatically produces a new
   ahmadfsbd/horizon-nexus:antelope-latest. The weekly cadence is intentional
   — Horizon upstream does not move fast enough to require daily checks.

   If the Docker Hub API returns an empty digest (API hiccup or rate limit),
   the check treats it as no change and skips that release until next week.
   This is a known limitation — a Docker Hub outage will not cause a false
   build but may delay detection by one week.

3. How to build locally:
     docker build --build-arg HORIZON_TAG=antelope -t horizon-nexus:local .

   Pre-compile SCSS before building locally:
     npm install -g sass
     sass overlay/themes/nexus/static/scss/nexus.scss \
          overlay/themes/nexus/static/css/nexus.css --no-source-map
     docker build --build-arg HORIZON_TAG=antelope -t horizon-nexus:local .

4. How to add a new OpenStack release:
     Add one entry to releases.json, create an empty digests/<tag>.txt, push.
     The pipeline picks it up automatically on the next run.

5. How to update theme colours:
     Edit overlay/themes/nexus/static/scss/_variables.scss, bump VERSION, push.
     All CI builds trigger automatically on the push to main.

6. How to replace the logo:
     Replace overlay/themes/nexus/static/img/logo.svg — no text accompanies
     the logo anywhere, it must remain a standalone mark with no wordmark.

7. Tagging strategy:
     <release-name>-<UI-version>  pinned, immutable, safe for production
     <release-name>-latest        floating, updated automatically by pipeline
     latest                       manual promotion only — you decide which
                                  release is the stable default

     Never use <release-name>-latest in production. Always pin to a specific
     version tag and promote deliberately.

8. How to plug into Kolla-Ansible:

     kolla_override_containers:
       horizon:
         image: ahmadfsbd/horizon-nexus:antelope-1.0

9. Customising accent colour and logo at deployment time without rebuilding
   the image — Kolla Config Injection:

   Kolla-Ansible has a built-in mechanism for injecting arbitrary files into
   containers at deploy time via the config/ directory. This allows operators
   to override the logo and accent colour for a specific environment without
   touching or rebuilding the image.

   HOW IT WORKS:
   Any file placed under /etc/kolla/config/horizon/ on the deployment host
   is copied into the running container at the matching path during
   kolla-ansible deploy. The image is never modified.

   OVERRIDING THE LOGO:
   Place a custom logo.svg on the deployment host at:

     /etc/kolla/config/horizon/themes/nexus/static/img/logo.svg

   Kolla copies this into the container at deploy time, replacing the default
   logo baked into the image. The file must be a valid SVG that works at
   32px height on the accent-coloured nav bar background.

   OVERRIDING THE ACCENT COLOUR:
   All accent colours in the image are defined as CSS custom properties in
   a standalone file: themes/nexus/css/nexus-vars.css

   To override colours for a specific deployment, place a replacement file
   on the deployment host at:

     /etc/kolla/config/horizon/themes/nexus/static/css/nexus-vars.css

   With contents such as:

     :root {
       --nexus-accent:        #7b3c7d;
       --nexus-accent-dark:   #5f2d5f;
       --nexus-accent-light:  #a35aa3;
       --nexus-accent-subtle: #f4e8f4;
     }

   Because nexus-vars.css is loaded last in base.html after the compiled
   theme CSS, these values take precedence over the compiled defaults with
   no rebuild required.

   BOTH OVERRIDES TOGETHER:
   A typical per-environment Kolla config directory looks like:

     /etc/kolla/config/horizon/
     └── themes/
         └── nexus/
             └── static/
                 ├── img/
                 │   └── logo.svg          ← customer logo
                 └── css/
                     └── nexus-vars.css    ← customer accent colours

   No image rebuild. No pipeline run. Just redeploy with kolla-ansible deploy.

10. Known limitations and operational notes:

    COLLECTSTATIC BUILD SHIM:
    The Dockerfile injects a minimal Django settings shim (DATABASES={},
    dummy SECRET_KEY) before running collectstatic so Django can initialise
    without a live database. This shim is removed after collectstatic completes.
    In rare cases, certain Horizon versions or installed plugins perform
    database introspection at startup even before collectstatic runs — if the
    build fails at this step, inspect the error and extend the shim settings
    to satisfy the specific requirement.

    UPSTREAM DIGEST CHECK RELIABILITY:
    The weekly upstream check hits the Docker Hub API directly. If Docker Hub
    returns an empty digest due to a rate limit or API change, the check
    silently skips that release until the following Monday. This will not
    cause a false build or broken image — it only delays detection by one week.

    SMOKE TEST DEPTH:
    The CI smoke test uses curl to check for the presence of id="nexus-nav"
    in the login page HTML response. This confirms the element is present but
    does not verify that static assets loaded correctly or that the nav is
    visually functional. The Playwright test in tests/smoke/check_ui.py
    provides deeper validation and should be run manually against a full
    deployment before promoting any image to production.

    BUILD FAILURE NOTIFICATIONS:
    If a build triggered by the upstream digest check fails the smoke test,
    a GitHub issue is automatically opened with a link to the failed run.
    Monitor these issues — a failure after an upstream Kolla update typically
    means a template block structure changed and one of your overrides needs
    updating.

    SCSS COMPILATION:
    SCSS is compiled in CI before the Docker build using the sass npm package.
    The Kolla base image does not include a Sass compiler. If you add new SCSS
    files, ensure they are imported in nexus.scss so they are picked up by
    the CI compile step.

11. Horizon functionality note:
    The overlay changes only visual presentation. Panel visibility, service-based
    tab enable/disable, and policy enforcement all remain driven entirely by
    upstream Horizon and Kolla's injected runtime settings. No functionality
    is modified. If a service is absent from the Keystone catalogue, its tab
    will not appear — exactly as it would in stock Horizon.

12. Never modify upstream files:
    Never edit any file inside the running container or inside the upstream
    Kolla base image directly. Changes made this way are lost on every
    redeploy and break reproducibility across nodes. All customisation must
    live in overlay/ and be applied through the pipeline. If you find yourself
    needing to change an upstream file, the correct path is to add a block
    override template in overlay/themes/nexus/templates/ instead.
